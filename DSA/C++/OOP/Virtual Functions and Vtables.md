# Virtual Functions and Vtables in C++

[OOP Four Pillars](<OOP Four Pillars.md#42-method-overriding-run-time-polymorphism>) showed **what** `virtual` does: through a base-class pointer or reference, a call runs the derived class's version. This note shows **how**. Choosing the function at runtime like this is called **dynamic dispatch**, and the mechanism C++ compilers use for it is the **vtable**, and it explains virtual functions' cost, their rules, and the bugs around them.

## Static Type vs Dynamic Type

Every pointer or reference has two types:

```cpp
Dog dog;
Animal& ref = dog;
Animal* ptr = &dog;
```

- The **static type** is what the declaration says: `Animal&`, `Animal*`. It's known at compile time.
- The **dynamic type** is the type of the object actually there: `Dog`. It's only known at runtime, in general.

```cpp
Animal* pick(bool b) { return b ? static_cast<Animal*>(new Dog) : new Cat; }
// the compiler can't know which type pick() returns: that's decided at runtime
```

- **Non-virtual** calls use the **static** type. The compiler picks the function and emits a direct call.
- **Virtual** calls use the **dynamic** type. The compiler emits code that looks up the right function **at runtime**.

## Static vs Dynamic Dispatch

**Dispatch** is the step that decides which function body a call actually runs. A call like `a.speak()` names a function, but when several classes define `speak`, something has to pick one. The two kinds of dispatch differ in **when** that choice is made and **which type** it's based on:

- **Static dispatch** (also called early binding): the compiler chooses at compile time, from the **static** type. Non-virtual member functions, free functions, overloads, and template calls are statically dispatched. The result is a direct call to a fixed address, which the optimizer can inline.
- **Dynamic dispatch** (also called late binding or dynamic binding): the choice is made at runtime, from the **dynamic** type. In C++, only calls to `virtual` functions through a pointer or reference are dynamically dispatched. The result is an indirect call, whose target is only known once the program is running.

```cpp
Animal* p = pick(user_input);   // dynamic type unknown until runtime
p->legs();    // static dispatch:  always Animal::legs, decided by the compiler
p->speak();   // dynamic dispatch: Dog::speak or Cat::speak, decided when this line runs
```

Dynamic dispatch is what makes run-time polymorphism possible: code written against `Animal&` can call behavior that was written later, in a class it has never heard of.

Dynamic dispatch is the **behavior**; the vtable is how C++ compilers **implement** it. The C++ standard only requires that the dynamic type's override runs, not how. Every major compiler uses vtables, and the rest of this note describes them. Other languages implement the same behavior differently: Python looks the name up in dictionaries at call time (see [How Python Compares](#how-python-compares)).

## The Flow of a Virtual Call

Here's what happens, from the call site to the function:

```text
a.speak()   where a is an Animal& referring to a Dog
   |
   | 1. read the hidden vptr stored at the start of the object
   v
Dog object:     [ vptr | ...Animal members... | ...Dog members... ]
                   |
   | 2. the vptr points to Dog's vtable: one table per CLASS, generated by the compiler
   v
Dog's vtable:   [ &Dog::~Dog | &Dog::~Dog (deleting) | &Dog::speak | ... ]
                                                            |
   | 3. load the entry at speak's fixed slot (here, index 2)
   v
   | 4. jump to that address
   v
Dog::speak()  runs
```

The compiler and the program each do part of the work:

- **At compile time**, for each class with virtual functions, the compiler builds one **vtable**: an array of function pointers, with one slot per virtual function. Each virtual function gets the **same slot index** in a base class's vtable and in all of its derived classes' vtables. A derived class's vtable copies the base's entries and replaces the slots it overrides.
- **At construction**, each object gets a hidden data member, the **vptr**, pointing at its class's vtable. A `Dog`'s constructor sets it to `Dog`'s vtable.
- **At the call**, the code doesn't know or care what the object is. It just follows `object → vptr → vtable[slot] → function`.

### Seeing the Vtable

Clang can print the vtables it generates:

```cpp
struct Virt {
    int hp;
    virtual void update() {}
    virtual void draw() {}
    virtual ~Virt() = default;
};

struct Guard : Virt {
    void update() override {}      // overrides update, inherits draw
};
```

```bash
clang++ -std=c++20 -Xclang -fdump-vtable-layouts -c vt.cpp -o /dev/null
```

```text
Vtable for 'Guard' (6 entries).
   0 | offset_to_top (0)
   1 | Guard RTTI                       <- type info, used by dynamic_cast and typeid
       -- (Guard, 0) vtable address --  <- the vptr points HERE
   2 | void Guard::update()             <- overridden: Guard's version
   3 | void Virt::draw()                <- not overridden: inherited from Virt
   4 | Guard::~Guard() [complete]
   5 | Guard::~Guard() [deleting]
```

`update` occupies the same slot in `Virt`'s vtable, but there it points to `Virt::update`.

### Seeing the Call

Compiling these two functions with `-O2` on an Apple Silicon Mac:

```cpp
struct Animal {
    virtual ~Animal() = default;
    virtual int speak() const { return 0; }
    int legs() const { return legs_; }        // non-virtual
    int legs_ = 4;
};

int call_virtual(const Animal& a) { return a.speak(); }
int call_plain(const Animal& a)   { return a.legs(); }
```

```text
call_virtual:
    ldr  x8, [x0]          ; 1. load the vptr from the start of the object (x0 = &a)
    ldr  x1, [x8, #16]     ; 2-3. load vtable slot 2 (16 bytes = 2 pointers past the vptr target)
    br   x1                ; 4. jump to whatever function that is

call_plain:
    ldr  w0, [x0, #8]      ; legs() was INLINED: just read legs_ at offset 8 (right after the vptr)
    ret
```

A virtual call is two memory loads plus an indirect jump. The non-virtual call disappeared entirely, because the compiler knew exactly which function it was and inlined it.

## How Python Compares

In Python, **every** method call is "virtual": every call is dynamically dispatched, and there's no static dispatch to opt into. `a.speak()` looks up `"speak"` in the object's `__dict__`, then walks the classes in the MRO, checking each class's `__dict__` (a hash lookup each time), until it finds it. Then it creates a bound method object and calls it.

A C++ virtual call is an array index done by the CPU in a few instructions. A non-virtual C++ call is a direct jump, or no call at all once inlined.

| | Python method call | C++ non-virtual | C++ virtual |
|---|---|---|---|
| Dispatch | Dynamic | Static | Dynamic |
| Lookup | Hash lookups along the MRO, at runtime | None: resolved at compile time | Two loads: vptr, then vtable slot |
| Can be inlined | No | Yes | Usually not (unless devirtualized) |
| Can be overridden | Always | No (only hidden) | Yes |

## The Costs of `virtual`

1. **Memory per object**: one vptr, 8 bytes on 64-bit, plus alignment padding:

    ```cpp
    struct Plain { int hp; void update() {} };            // sizeof = 4
    struct Virt  { int hp; virtual void update() {} };     // sizeof = 16: 8 vptr + 4 hp + 4 padding
    ```

    For millions of small objects (particles, tiles), that's significant. See [Object Memory Layout](<../Memory/Object Memory Layout.md>).

2. **Memory per class**: one vtable, shared by all objects of the class. Negligible.

3. **Call overhead**: the extra loads, plus an indirect branch the CPU has to predict. That's small by itself, a few nanoseconds at most.

4. **No inlining**: this is usually the **biggest** cost. Because the target isn't known at compile time, the optimizer can't inline the function body into a hot loop, which also blocks the optimizations that inlining enables.

This is why C++ makes `virtual` **opt-in**: classes that don't need runtime polymorphism shouldn't pay for it (the zero-overhead principle from [What is C++](<../Fundamentals/What is C++.md#4-zero-overhead-abstraction>)).

### Devirtualization

When the compiler **can** prove the dynamic type, it turns dynamic dispatch back into static dispatch: a direct call, which can then be inlined:

```cpp
Dog d;
d.speak();               // called on an object, not through a pointer or reference: the type is exactly Dog

class Dog final : public Animal { ... };
void f(Dog& d) { d.speak(); }   // final: nothing can derive from Dog, so Dog::speak is the only possibility
```

Marking leaf classes `final` helps the optimizer.

## Rules That Follow From the Mechanism

### Virtual Calls in Constructors and Destructors Don't Dispatch to Derived Classes

The vptr is set **in stages** as the object is constructed (see the construction order in [Object Lifetime and RAII](<Object Lifetime and RAII.md#2-the-order-of-construction-and-destruction>)). While the base-class constructor runs, the vptr still points to the **base** vtable, because the derived part doesn't exist yet:

```cpp
struct Base {
    Base() { hello(); }                                   // virtual call from a constructor
    virtual void hello() { std::cout << "Base::hello\n"; }
    virtual ~Base() = default;
};

struct Derived : Base {
    void hello() override { std::cout << "Derived::hello\n"; }
};

Derived d;     // prints "Base::hello", not "Derived::hello"
d.hello();     // prints "Derived::hello"
```

Calling a derived override before the derived members were constructed would be unsafe, so C++ deliberately doesn't. The same applies in reverse in destructors. **Python differs here**: a method called from a base `__init__` does dispatch to the subclass's override.

Calling a **pure** virtual function from a base constructor crashes with `pure virtual function called`.

> This is one reason Unreal asks you to put gameplay setup in `BeginPlay()` rather than the constructor. The constructor runs while the object is still being built (and also when Unreal creates the class's default object), whereas `BeginPlay` runs on a fully constructed actor that's in the world.

### Why Base Classes Need Virtual Destructors

`delete base_ptr;` is itself a call through the base type. If the destructor isn't virtual, the compiler calls `Base::~Base` directly, using the **static** type, and the derived destructor never runs. With `virtual ~Base()`, the destructor gets a vtable slot (the `[deleting]` entry above), so `delete` dispatches to `~Derived()`, which then runs `~Base()` automatically. See [OOP Four Pillars](<OOP Four Pillars.md#44-virtual-destructors>).

### Why Slicing Loses Polymorphism

Copying a `Dog` into an `Animal` value creates a **new `Animal` object**, whose constructor sets its vptr to **`Animal`'s** vtable. The copy is a real `Animal`, not a disguised `Dog`, so its virtual calls go to `Animal`'s versions. Pointers and references don't create new objects, so they keep reaching the original vptr.

### Overriding Requires an Exact Signature Match

The derived function only takes over the base's vtable slot if the name, parameter types, and `const`-ness all match. Otherwise it's a brand-new function with its own slot (or no slot at all), and the base version keeps running. `override` turns that silent mistake into a compile error.

## Runtime Type Information (RTTI)

The vtable's RTTI entry is what makes these work at runtime:

```cpp
#include <typeinfo>

Animal* p = new Dog;
typeid(*p) == typeid(Dog)     // true: the dynamic type (requires a polymorphic class)
typeid(*p).name()             // implementation-specific (mangled) name, like "3Dog"
dynamic_cast<Dog*>(p)         // checks RTTI; returns nullptr if *p isn't a Dog
```

> Unreal compiles with RTTI turned off by default, so `dynamic_cast` and `typeid` aren't available on `UObject`s. `Cast<T>()` and `IsA<T>()` use Unreal's own reflection data instead.

## Alternatives to Virtual Dispatch

When the set of types is closed and known in advance, these avoid vtables entirely:

- **Templates** (compile-time polymorphism): the type is fixed per call site, so calls are statically dispatched and can be inlined. See [Templates](<../Fundamentals/Templates.md>).
- **`std::variant` + `std::visit`**: holds one of a fixed set of types by value, with no heap allocation and no slicing.
- **Data-oriented design**: store each kind of object in its own contiguous array and process each array in its own loop. That's common in high-performance game code, such as Unreal's Mass framework.

## Summary

```text
Object:       [ vptr | members... ]      vptr: 8 hidden bytes per object of a polymorphic class
vptr   ->     the class's vtable         one per class: slots of function pointers, plus RTTI
Call:         obj -> vptr -> vtable[slot] -> jump

Static type   (what the code says)       -> used by non-virtual calls: static dispatch, chosen at compile time
Dynamic type  (what the object is)       -> used by virtual calls:     dynamic dispatch, chosen at runtime

Cost:         8 bytes per object, an indirect call, and (mostly) lost inlining
Rules:        virtual destructor in base classes; use override; no derived dispatch in ctors/dtors;
              pass by pointer/reference to avoid slicing
```
